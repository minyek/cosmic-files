# #57 Pausing, resuming and cancelling file operations misbehave [CLOSED]

## Problem

Pausing, resuming and cancelling file operations went wrong in five ways:

1. Pausing a delete froze every other file operation until the delete resumed.
2. Pausing or resuming could restart an operation that had just been cancelled or had failed. "Resume all" in particular brought a cancelled operation back.
3. A pause, resume or cancel that arrived just as an operation checked its state could be lost, leaving the operation paused.
4. Cancelling a paused copy that uses the gio fallback (phones and cameras over MTP, gvfs FUSE read errors, destinations that fail to open, unsupported writes) left the copy waiting for a resume that never came.
5. Resuming such a paused gio copy froze every file operation.

## Cause

All file operations run on one compio runtime thread (`src/app.rs`).

1. The Delete loop in `Operation::perform` (`src/operation/mod.rs`) waited out a pause with `futures::executor::block_on(controller.check())`, which blocked that thread. compio 0.19, which #56 adopts, also caps at 64 the queue that other threads use to wake its tasks, and spins the waker while the queue is full. So enough wakes during such a pause could hang the waking thread too.
2. `Controller::unpause` (`src/operation/controller.rs`) tested `!is_cancelled() | !is_failed()`, which is always true. `pause` stored Paused over any state, and the UI still offers Pause and Resume until the task sees the cancel.
3. `check`, `until_paused` and `until_unpaused` read the state first and only then created the tokio `Notified` future. A change that landed between the two was never seen.
4. The gio copy (`Op::gio_file_copy`, `src/operation/recursive.rs`) waited out a pause with `until_unpaused`, which keeps waiting while the operation is cancelled or failed.
5. The copy's glib-side loop kept the watch channel's read guard from `wait_for` alive while it waited for the resume, because `futures::select!` holds an arm's output until the arm body ends. The runtime thread's `send(false)` then blocked for ever on the write lock. Once the channel closed, the loop also spun, because both of its waits returned at once.

## Fix

1. The Delete loop awaits `controller.check()`.
2. `pause` and `unpause` share one compare-and-swap transition (Running ↔ Paused) that wakes waiters only when it changes the state.
3. The three waits share `wait_for`, which creates the `Notified` before it reads the state.
4. The gio copy waits out a pause with `check()` and ends with the cancel.
5. The glib-side loop became `run_pausable`. It drops the guard before waiting and ends when the channel closes.

Landed in f4ff95d, together with #56. The compio 0.19 bump in #56 is what made fix 1 urgent, and reviewing it found the other four.

## Acceptance criteria

- While a delete is paused, other tasks on the runtime keep running; a resumed delete carries on, and a cancelled one reports the cancel.
- Pausing or unpausing never changes a cancelled or failed operation.
- A state change made between reading the state and waiting still ends the wait.
- A paused gio copy finishes after a resume, and ends after a cancel, without freezing the runtime or spinning.

## Tests

- `operation::tests::a_paused_delete_leaves_the_runtime_free` and `a_resumed_delete_carries_on`. With `block_on` put back, both hang.
- `operation::controller::tests::pausing_a_cancelled_operation_keeps_it_cancelled`, `pausing_a_failed_operation_keeps_it_failed`, `unpausing_a_cancelled_operation_keeps_it_cancelled` and `unpausing_a_failed_operation_keeps_it_failed`. All four failed before the fix. With them: `unpausing_a_paused_operation_resumes_it`, `a_resume_wakes_a_waiting_check`, `a_change_between_reading_the_state_and_waiting_is_not_lost` and `a_cancel_ends_a_wait_for_resume`, which poll by hand, so a lost wake fails instead of hanging.
- `operation::recursive::tests::a_paused_copy_finishes_after_a_resume`, `a_cancelled_paused_copy_ends` and `a_copy_ends_when_its_controller_goes_away`. On the old loop all three hang.
- Checked by hand: a real 1 GiB `gio_file_copy` on local files under `GIO_USE_VFS=local`; after pause and resume it finished; after pause and cancel it ended with the cancelled error, the runtime thread stayed free, and no CPU was used afterwards.

## Not fixed here

Tracked in #58: a cancelled copy is reported as failed; pausing a gio copy does not stop gio's transfer; a panic on the glib thread panics the runtime thread.
