# #55 Deletes the Trash cannot take were labelled "Move to Trash", and a trashed folder's children were trashed again [CLOSED]

## Problem

Some delete entries still said one thing and did another after the "Delete permanently" menu fix (#54):

- On a network or GVFS mount, "Move to Trash" opened the "Permanently delete?" dialog, because files there cannot go to the Trash.
- Inside a folder opened from the Trash, the menu bar offered "Move to Trash", and it and the Delete key moved the children into the Trash again. The right-click menu for the same files said "Delete permanently".
- A dangling symlink found by search read "Move to Trash" but was sent to the permanent-delete dialog.

## Cause

The menus chose their entry from the location and the Shift key only. `App::delete` (`src/app.rs`) decides by stat-ing each path: files on non-local filesystems go to the permanent-delete dialog. A folder opened from the Trash is a plain path location, so its children (which carry trash metadata) took the trash path again. Classification also followed symlinks, so a link to a missing target failed the stat.

## Fix

`ItemMetadata::can_trash` (`src/item/metadata.rs`) answers from an item's cached metadata: a local path can be trashed; trash entries, GVFS and network entries cannot. `deletion_of` (`src/menu.rs`) turns the selection into `FromTrash`, `ToTrash` or `Permanent`, and `delete_entry_of` gives the menu bar and every context-menu delete entry the same label and action. A non-empty selection that the Trash can take none of reads "Delete permanently" and fires `PermanentlyDelete`, with or without Shift. `Message::Delete` sends such items straight to the permanent-delete dialog and classifies the rest with `symlink_metadata`, so a local link is trashed itself. A mixed selection still reads "Move to Trash": its local items are trashed and the dialog asks about the rest. No new disk access happens on the UI thread.

Landed in d70f661.

## Acceptance criteria

- A non-empty selection of which no item can be trashed (a network or GVFS mount, a trashed folder's children) shows "Delete permanently" in the menu bar and the context menu, with or without Shift.
- A selection with at least one trashable item keeps the Shift rule; an empty selection counts as trashable.
- The Trash location keeps "Delete permanently" with the delete-from-trash dialog.
- The Delete key on a trashed folder's children opens the permanent-delete dialog for them and trashes nothing; local items selected with them are still trashed.

## Not fixed here

- Dragging a trashed folder's child onto the Trash still moves it into the Trash again.
- The menu bar offers "Restore from trash" only in the Trash location, while the right-click menu also offers it for a trashed folder's children; whether restore works for those children is unverified.
- A symlink stored on a network mount whose target is local reads "Move to Trash" but gets the permanent-delete confirmation.
