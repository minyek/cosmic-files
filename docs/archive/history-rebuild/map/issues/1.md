# #1 Multi-selection properties pane froze the UI with thousands of owner/group lookups per frame [CLOSED]

## Problem

Selecting many files with the details pane open froze the window. In a directory of about 17,000 entries on a busy disk, the main thread sat at roughly 97% CPU. The disk was not the bottleneck: the process read nothing from it.

## Cause

`Tab::multi_preview_view` runs on every frame while a multi-selection is shown. For each selected item it called `uzers::get_user_by_uid` and `uzers::get_group_by_gid`. Each call goes through `getpwuid_r` / `getgrgid_r`, which reads `nsswitch.conf`, `/etc/passwd` and `/etc/group`.

Measured on the running binary:

- `strace` of the main thread showed about 1,400 reads a second of those three files.
- A stack sample put the thread in `getgrgid_r`, called from `multi_preview_view`.

## Fix

The pane now collects the distinct uids and gids of the selection and resolves each name once, through a small `distinct_names` helper. The displayed owners and groups are unchanged, and an id that does not resolve still shows as an empty name.

Landed in 8bbce58.

## Acceptance criteria

- For N selected items that share one uid and gid, the name lookup runs once per distinct id, not once per item.
- The displayed owner and group sets are unchanged.

## Tests

- `owner_names_resolve_once_per_distinct_id` fails against the per-item version (1000 lookups, expected 3).
- `owner_names_keep_unresolvable_ids_as_empty` pins the empty-name fallback.

## Not fixed here

- The single-item details pane still does one owner and one group lookup per frame. That is negligible, but a cache of id to name would remove it.
- `multi_preview_view` still does work proportional to the number of selected items on every frame, such as one `mime.to_string()` allocation per item. This has not been measured. Measure with a large selection open before deciding whether it needs a fix.
